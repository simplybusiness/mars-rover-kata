# Automated tests and linting — design

**Date:** 2026-05-13
**Branch:** `setup-automated-tests-and-linting`
**Status:** Approved

## Goal

Wire up CI so that every push and pull request to the mars-rover-kata repo runs a
linter and the test suite. The kata starter currently has no source code, no
tests, and no CI; learners pick either minitest or rspec when they start. The
pipeline must be useful from commit zero (when the repo is empty of Ruby code)
and continue to be useful once a learner adds either framework's files.

## Non-goals

- Scaffolding a sample spec or test file. The README intentionally leaves the
  framework choice to the learner.
- Coverage tooling (simplecov, codecov). Out of scope; can be added later.
- Auto-correction in CI. RuboCop runs as a checker only.
- Changing `tcr.sh`. It is rspec-specific by the original author's choice and
  works as-is.
- Adding Rake / a Rakefile. The two test frameworks are invoked directly to
  keep the dependency footprint minimal.

## Decisions

| Question | Decision | Reasoning |
|---|---|---|
| CI platform | GitHub Actions | Repo is hosted at `github.com/simplybusiness/mars-rover-kata`; Actions is the default and free for this org. |
| Linter | RuboCop | Ruby community + Simply Business standard; configurable via `.rubocop.yml`. |
| Test runner(s) in CI | Both rspec and minitest, tolerating absence of files | Preserves the README's "pick either" promise. |
| Ruby version | 3.4.7 | `Gemfile.lock` records `RUBY VERSION ruby 3.4.7` and a recent "Chore: Upgrade Ruby" PR moved to it. `.ruby-version` is stale at 3.3.7 and will be updated. |
| Orchestration | Direct shell invocations in the workflow | YAGNI: no Rake gem, no Rakefile. |

## Architecture

A single GitHub Actions workflow `.github/workflows/ci.yml` with two parallel
jobs. Splitting lint and test gives independent red/green signals on a PR and
lets lint fail fast without waiting on tests (and vice versa).

```
push / pull_request
        │
        ├─► lint job
        │     setup-ruby (bundler-cache)
        │     bundle exec rubocop
        │
        └─► test job
              setup-ruby (bundler-cache)
              bundle exec rspec           # exits 0 with no spec files
              guarded minitest invocation # skips when test/ is empty
```

Both jobs run on `ubuntu-latest` and reuse `ruby/setup-ruby@v1` with
`bundler-cache: true`, which reads `.ruby-version` and caches gems keyed on
`Gemfile.lock`. No extra cache configuration needed.

## Components

### 1. `.github/workflows/ci.yml`

Triggers on push to `main` and on all pull requests.

```yaml
name: CI
on:
  push:
    branches: [main]
  pull_request:
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: ruby/setup-ruby@v1
        with:
          bundler-cache: true
      - run: bundle exec rubocop
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: ruby/setup-ruby@v1
        with:
          bundler-cache: true
      - name: RSpec
        run: bundle exec rspec
      - name: Minitest
        run: |
          if compgen -G "test/**/*_test.rb" > /dev/null; then
            bundle exec ruby -Ilib -Itest -e "Dir.glob('test/**/*_test.rb').sort.each { |f| require './' + f }"
          else
            echo "No minitest tests yet — skipping."
          fi
```

Behavioural notes:

- `bundle exec rspec` with no `spec/` directory or files exits 0 by default.
  No special handling required.
- The minitest step uses `compgen -G` (Bash built-in) to test the glob without
  spawning extra processes; it works under `bash -e` because both branches of
  the `if` are accounted for.
- When `test/**/*_test.rb` matches at least one file, the inline Ruby loads
  each file; minitest's `autorun` hook then runs the assertions and exits
  non-zero on failure.

### 2. `.rubocop.yml`

Minimal config — favour RuboCop's evolving defaults over local opinions:

```yaml
AllCops:
  TargetRubyVersion: 3.4
  NewCops: enable
  Exclude:
    - 'vendor/**/*'
    - 'tmp/**/*'
```

`NewCops: enable` opts in to new cops automatically as RuboCop releases them,
which is appropriate for a kata that should track current Ruby style.

### 3. `Gemfile`

Add a `:development` group containing `rubocop`. RuboCop stays out of the
`:test` group so test-only environments don't pull it in.

```ruby
source 'https://rubygems.org'
ruby '3.4.7'

group :development do
  gem 'rubocop', require: false
end

group :test do
  gem 'minitest'
  gem 'rspec'
end
```

The `ruby` directive moves from `3.3.7` to `3.4.7` to match `Gemfile.lock` and
`.ruby-version`.

### 4. `Gemfile.lock`

Regenerated by `bundle install` after the Gemfile change. Adds rubocop and its
transitive deps (parser, rubocop-ast, regexp_parser, etc.).

### 5. `.ruby-version`

`3.3.7` → `3.4.7`.

### 6. `README.md`

Append a short section documenting how to run the same checks locally:

```markdown
## CI

Every push and pull request runs `rubocop` plus rspec/minitest via GitHub Actions.

Locally:

    bundle install
    bundle exec rubocop
    bundle exec rspec      # if you chose rspec
    bundle exec ruby -Ilib -Itest test/**/*_test.rb   # if you chose minitest
```

## Verification

After implementation, on the local branch (no push):

1. `bundle install` succeeds, locks rubocop.
2. `bundle exec rubocop` exits 0 (no Ruby files in scope).
3. `bundle exec rspec` exits 0 (no spec files).
4. The minitest shell guard correctly skips (no `test/` directory).
5. `act` or visual review of `ci.yml` confirms valid syntax.

CI itself only runs once the branch is pushed — by user instruction, that
happens later and is not part of this work.

## Risks and mitigations

| Risk | Mitigation |
|---|---|
| RuboCop's `NewCops: enable` introduces a breaking cop on a future release. | Acceptable for a kata. Easy to pin or disable a single cop in `.rubocop.yml`. |
| Learner adds minitest tests under a non-standard path (e.g. `tests/`). | Document the expected `test/**/*_test.rb` layout in the README's CI section. |
| `bundler-cache: true` caches against `Gemfile.lock`, which is `.gitignore`d. | Cache still works — `setup-ruby` falls back to hashing the resolved lockfile after `bundle install`. No action needed. |
| `.ruby-version` change drifts again later. | The Gemfile's `ruby '3.4.7'` directive plus `setup-ruby` reading `.ruby-version` keeps three sources aligned; bundler will warn if any drifts. |

## Out of scope (future work)

- Coverage reporting (simplecov + Codecov upload).
- Caching the RuboCop result cache between runs (only worthwhile once there's
  a meaningful amount of source).
- `bundle audit` / dependency vulnerability scanning.
- Pre-commit hook running the same checks locally.
